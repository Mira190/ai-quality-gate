# 架构

ai-quality-gate 是一个对**整个仓库**做 full review 的 GitHub Action，为 shift left 服务：每个 PR 上都跑一遍（也可定时、手动），回答三个问题。

1. **证明**：每条需求、每个设计决策，有没有测试能证明它？
2. **层级（placement）**：每件事是不是在合适的层级测的（unit / component / integration / e2e）？
3. **CI**：lint、type check、测试等检查，是不是真的在 PR 上强制执行？

本文说明它为什么这样设计。需求见 [requirements.md](requirements.md)，本仓库用自己审查自己。

## 第一性原理

审查结论要能拦住合并，就必须满足三件事：**可重复**（同样的输入得到同样的结论）、**可核对**（每条结论指向一行文档、一行测试或一行 workflow）、**便宜**（每个 PR 都跑，仓库再大也跑得动）。模型在这三件事上都弱于代码，所以分工很简单：

| 问题 | 谁来定 | 为什么 |
| --- | --- | --- |
| 文档里哪些是规则、规则 ID、是否 critical、规则写了哪些限值 | 代码 | 规则的身份不能变，否则 baseline、缓存、suppress 全部失效 |
| 测试用例在哪、是否 skip、有没有断言、需要什么才能跑（层级） | 代码 | 解析即可 |
| 测试名字里带了规则 ID → 链接 | 代码 | 这是事实 |
| CI 是否在 PR 上跑、失败会不会被忽略、`npm run lint` 实际执行什么 | 代码 | 解析 YAML 和脚本即可 |
| Placement（测高了、只对着 mock 测、放错目录） | 代码 | 输入全是上面的事实 |
| 优先级 P0–P3、是否阻断、报告里的每个数字 | 代码 | 查表 |
| **没带 ID 的测试，到底有没有断言这条规则？** | **模型** | 需要读懂语义 |
| **这句话是不是一条可测的行为？最低能在哪一层证明？** | **模型**（顺带，同一次调用） | 需要读懂语义 |

模型只做最后两行，而且它的回答要过代码的核对才算数。

## 流水线

```
scan → extract → index → ci → trace(link → judge → assess) → placement → gate → report
```

| 阶段 | 输入 | 输出 | 模型 |
| --- | --- | --- | --- |
| scan `src/scan` | `git ls-files -s` | 文件清单：按路径分成 doc / test / source / ci / manifest / config，包与语言 | 否 |
| extract `src/extract` | 文档 | 规则（需求、决策）、风险标签、性质、限值 | 否 |
| index `src/index` | 测试文件 | 用例（名字、行号、skip、断言数、参数行数、提到的规则 ID）、文件所需层级、是否 mock、import | 否 |
| ci `src/ci` | workflow、package.json、Makefile | 每项检查的状态：enforced / 失败被忽略 / 不在 PR 上 / 配置了没跑 / 缺失 | 否 |
| trace `src/trace` | 规则 × 用例 | 每条规则的证明记录：proven / hole / no test / unverified | **仅 judge** |
| placement `src/placement.js` | 证明记录、层级 | placement finding、各层用例数 | 否 |
| gate `src/gate.js` | finding、diff、baseline | 每条 finding 是否阻断、verdict | 否 |
| report `src/report` | ledger | report.md、comment.md、findings.json、results.sarif | 否 |

## 设计决策

每个决策都有 ID，证明它的测试带着这个 ID。

- **DEC-1 模型不写报告。** 报告里的每个数字、优先级、排序和表格都由代码从 ledger 渲染；同一个 ledger 渲染出的报告逐字节相同。
- **DEC-2 规则抽取是确定性的。** 规则只来自四种代码能识别的形态：带 ID 的条目、ADR、规范性句子、验收标准列表；无 ID 规则的 ID 是其文本的哈希，所以句子在文档里挪位置不会变成另一条规则。
- **DEC-3 模型只看片段。** 发给模型的是代码筛出的少数候选用例的带行号片段，不是文件，更不是仓库；提示里声明片段是数据，其中的指令不得执行。
- **DEC-4 结论按输入内容缓存。** 每条规则的模型结论以"规则文本 + 候选用例片段"的哈希为键写入缓存；输入不变就不再调用模型，结论也不变。
- **DEC-5 模型没有工具。** Copilot CLI 作为子进程以非交互模式在空目录里运行，不授予任何工具，只带最小环境变量；作业里的其它密钥不会传给它。
- **DEC-6 解析结果按 blob 哈希缓存。** 文档和测试文件的解析结果以 git blob 哈希为键写入缓存；PR 只重新解析它改动的文件，源码文件根本不读。
- **DEC-7 阶段独立降级。** 某个阶段抛错、模型调用失败或超时，报告的 Run 一节写明跳过了什么，其余阶段照常出结果；gate 自己坏了不会让构建失败。
- **DEC-9 模型结论可以提交进仓库。** `aqg run --write-lock` 把本次依赖的模型结论写进 `.quality-gate.lock.json`；之后任何机器、空缓存、没有模型，都从这个文件得到同样的结论。
- **DEC-8 证据分级。** 每条 finding 带证据级别：E（执行）、S（代码判定）、V（模型提出、代码核对）、A（建议）；建议不能阻断，也永远不是 P0。

## 模型的使用：省 token、少变数、不可被说服

**只问需要问的。** 进入 judge 的规则必须：没有任何测试提到它的 ID；默认还要求它是 critical（`ai.scope: all` 可放开）。按 ID 打标的仓库，模型调用次数是 0——本仓库就是。

**先问最严重的，问不完的下次接着问。** critical 在前。预算（`ai.max_requests`、`ai.max_rules`、`ai.deadline_s`）用完后，剩下的规则标为 unverified 并计数；已判定的进了缓存，下一次运行从没判过的继续。大仓库因此是几次运行收敛，而不是一次付清（GATE-9）。

**一次问多条，每条只带片段。** 每次调用 6 条规则，每条最多 4 个候选用例，片段的挑法见下一小节。一次调用同时回答三件事（是否可测、哪个候选证明了它、最低能在哪层证明），placement 需要的模型输入不另花 token。

### 读什么，给模型看什么

模型从不读文件。让模型自己翻文件，它读多少、读到哪停每次都不一样，也无从核对；所以读文件是代码的事，代码每次都读完，模型只看代码挑出来的片段。

**找到该读的文件**（不用模型）：路径分类只留文档、测试、CI 文件；规则 ID 用一次 `git grep` 找出所有提到它的文件；规则到候选测试有两条路——倒排索引按规则里最稀有的词检索，以及"规则的词命中源码文件名 → 导入该源码的测试"（GATE-25），后者专治测试用词和需求用词不同。

**挑出最重要的部分**（GATE-24）：
- 放得下的用例整段展示（去掉空行和纯注释行）。
- 放不下的保留开头、每一行断言及其上一行，再按"与规则共有的词数"补充其余行，直到预算用完。断言里提到规则用词的排在前面。行号都是文件里的真实行号。
- 用例通过 helper 做的断言（`expectCapped(order)` 这一类）一并展示：同文件的 helper，以及测试 import 的 helper 文件里的（一跳）。调用 helper 的那一行算作这个用例的断言，可被引用。
- 用例上方最近的 setup 块（`beforeEach` 等）展示几行：断言的对象是它造出来的。
- 规则带着它所在的章节标题（"Pricing › Discounts"）：脱离上下文的一句话只是半条规则。
- 回复格式要求先填证据（引用的行）再填结论：模型是从左到右生成的，先找到证据再下结论，比先下结论再找理由更稳。
- 如果断言多到预算放不下，片段里写明还有多少行断言没展示，并且模型关于这个用例的"没有证明"不作数，降为建议。看到的部分可以证明，没看到的部分不能用来否定。

报告的 Run 一节写明：代码完整读了多少文件；给模型看了多少个候选、其中多少行；是否每个候选的断言都展示全了。

### 用词不同时怎么找到对应的测试

规则说"永不重复发送同一条消息"，测试叫"每个 send ID 只发一次"；规则说 acknowledging，测试写 acks。词面检索在这里会漏，漏了就会把有测试的规则说成没有。四层办法，前三层不依赖仓库、不花 token：

1. **词族归一。** 屈折变化和常见派生都归到同一个词干：walk / walked / walker；configure / configuration / configurable；valid / validate / validation / validator；sent → send、paid → pay 这类不规则形式查表。
2. **缩写归一。** 一张固定表（约 130 项）：msg ↔ message、cfg ↔ configuration、ack ↔ acknowledge、db ↔ database……只收在软件里含义唯一的缩写；res（response / result / resource）、req（request / requirement）这类有歧义的故意不收。缩写只按书写形式匹配，不按词干："state"不会被当成"stat"。
3. **同一件事的两种说法。** 一张固定的概念表（34 个概念、约 370 个词）：次数（once / twice / duplicate / repeat）、不丢（lost / keep / survive）、崩溃恢复、拒绝与允许、限值、先后顺序、等待与超时、重试、增删改、撤销、启停、显示与隐藏、存储、收发、鉴权、并发、金额、速度等。一个词只属于一个概念。动词加小品词分开写等于合起来写："times out"就是"timeout"，"rolls back"就是"rollback"。"each other"作为一个词保留。

这三张表都在 `src/lexicon.js`，文件头写明了修改它的规矩：只能因为一个词在软件里普遍是这个意思而加，不能因为某个仓库的某个测试没匹配上而加。守这条规矩的是 `tests/fixtures/paraphrases.js`：32 对来自互不相关领域（电商、账号、消息、文件、排期、并发、界面）的"规则 / 测试名"，都不取自 gate 跑过的任何仓库，另有 6 条在测试池里没有对应测试的规则。当前成绩：28 对能被找到（20 对排第一），6 条无关规则没有一条被错配候选。剩下 4 对是纯改写（"提前一刻钟提醒"对"会议开始前 15 分钟"），词表不该去凑，留给模型。

4. **排序看广度。** 候选按"说到了规则里几样不同的东西"排，其次才是词的稀有程度；测试名字里说到的算一份，只在正文里出现的算半份；只共有概念而没有共有词的，再减半——概念是线索，不是证据。所以"sends a message once per send ID"排在"can be stopped twice"前面。
5. **第二次阅读看得更宽（GATE-30）。** 第一次阅读没找到证明时，第二次阅读除了原来的候选，还会看到后面二十行以内的"次近"测试，这个圈按"在本仓库里常一起出现的词"排序（规则说 walkers，仓库里 walkers 常和 crowd 一起出现）。它在这个圈里引用的断言通过核对后，就是一条正常的链接。

约束：没有模型时一条规则算不算"有候选"，只由前四层决定，与测试集里别的内容无关；仓库自己的词汇关联只影响第二次阅读看什么。这样加一个无关的测试不会让别的规则在"没有测试"和"未核实"之间翻转（评分卡守着这一条）。

**回答要过核对。** 模型说"已证明"必须引用它被展示过的候选用例、被展示过的行，且那一行（或相邻两行内）是断言。任何一条不满足，结论降为建议，不计入证明，也不能阻断。仓库里的文字无法让 gate 放行。

**"没有证明"要读两遍（GATE-21）。** "没有任何候选证明它"无法附带引用，是唯一只凭模型一面之词的结论。当词法检索认为存在强相关候选、而模型全部否定时，gate 换一个问法、把候选倒序，再问一次："找出会因规则被破坏而失败的那一行断言，没有就回答 null"。两次一致才算 V 级并可阻断；不一致降为建议。没有候选或只有弱候选时，词法检索本身已经同意，不需要第二次。

**结论只产生一次。** 每条规则的结论按"规则文本 + 候选片段"的内容哈希缓存（DEC-4），模型名不进键：换模型不会让已核对的结论全部重开。再进一步，`--write-lock` 把结论提交进仓库（DEC-9），评审时在 diff 里就能看到模型认定了什么。

**调用外面的 harness（GATE-22）。** 超时、重试；回复不是要求的 JSON 时带着错误原因重问一次；连续两次调用失败、或一次鉴权失败，本次运行不再调用模型；整个阶段有截止时间。任何一种情况下，代码判定的 finding 不受影响，报告的 Run 一节写明停在哪里。

**模型能改变什么。** 只有三件事：把候选测试确认为链接（需引用）、确认"最近的几个测试都没断言它"（需两次一致）、判定一句话不是可测行为（无 ID 的从统计中去掉，有 ID 的变成"需要改写"的建议）。它不能新增规则，不能改优先级，不能改 CI 和 placement 的事实。

### Provider

| provider | 用途 |
| --- | --- |
| `copilot` | 生产用。`copilot -p <prompt> -s --no-ask-user --deny-tool=…`，用带 "Copilot Requests" 权限的 fine-grained PAT（`COPILOT_GITHUB_TOKEN`）认证 |
| `command` | 任何"stdin 读提示、stdout 写回答"的程序 |
| `handoff` | 没有模型时：跑不出答案的提示写到 `out/ai-requests.json`，由人或 coding agent 把回答写进 `ai-answers.json`，下次运行读取。测试里的录制回答也走这条路 |
| `none` | 只出代码判定的 finding |

`auto`（默认）：装了 CLI 且有 token 用 copilot，否则有回答文件用 handoff，否则 none。没有模型时 gate 照常运行，只是需要语义判断的规则显示为 unverified。

## 不按常规写的仓库

在一个真实仓库（一个 3D 城市游戏，3500 个文件，文档是叙述体，测试是自己写的检查程序）上跑出来的三条经验，都已变成规则：

- **检查程序也是测试（GATE-29）。** 测试不一定叫 `*.test.*`。CI 里某一步运行的、名字是 check / test / verify / probe 的程序就是测试。它的用例是那些"用一句话说明自己在查什么"的断言：`check(lights === before, 'the number of lights never changes')` 是一个以这句话命名的用例。脚本自己的断言函数（调用三次以上、第一个参数是条件、最后一个参数是句子）自动识别。这样一个两千行的检查程序是两百多个一行的用例，而不是一个两千行的用例。
- **CI 跑的 shell 脚本要跟进去（GATE-14）。** workflow 只写一行 `tools/check.sh`，真正跑什么在脚本里。
- **句子要读完整（GATE-3）。** 文档按列宽硬换行，一行不是一句；先把段落和列表项拼回去再切句。"cannot"多半在描述世界而不是规定软件，不算规范性词。`docs/` 下没有被命名为需求或设计的文档按设计文档读。

候选数量按行数预算而不是按个数：一个三十行的测试是一个候选，一行的检查只占它的三十分之一，同样的 token 能给模型看十几个。看到的候选越对，"没有测试"越不容易说错。

没有 ID 的句子即使被模型判为"可测但没有测试"，也只有 critical 的才成为 finding；其余只进 Proof 表。理由：这个结论依赖"最近的几个测试正好是该看的那几个"，没有 ID 时这个前提不够硬。

## 形式化模型（GATE-31）

仓库里有 TLA+ 模型时，配置文件（`.cfg`）里列出的每个 INVARIANT / PROPERTY 是一条设计决策，文字取自它定义上方的注释。它要两种证明：

- **模型检查器在 CI 里跑**，证明设计守得住它。只靠人手动跑时，报一条 `ci.specs`（P1），列出只靠它证明的全部性质，而不是每条性质报一次。
- **代码里的测试**，证明实现遵守设计。和普通规则一样找候选、交给模型判断；测试里直接写了性质名字的，按名字链接。

## 执行证据（可选，GATE-26）

读得再仔细也分不清两种测试：一个真的守住了"折扣不超过 20%"，另一个名字对、数字对、也有断言，但把上限改成 21 它照样通过。分清它们的唯一办法是跑一下。

给了测试命令（`execute.test_command`，Action 的 `execute` + `test-command`）后，对每条"写了限值、有链接测试、能找到实现文件"的规则：在实现代码里找到那个限值起决定作用的一行，挪一步（20 → 21），只跑链接的测试，然后恢复文件。

- 有测试失败 → 证明升级为执行证据（E）。
- 全部通过 → `proof.survived`，critical 规则是 P0：证据是一次测试运行，不是谁的判断。

为了便宜和安静，照搬 Google 做 mutation testing 的纪律：每条规则只做一个 mutant；跳过日志、字符串、注释、import 这类不值得测的行；只跑链接的测试；结果按规则、代码、测试的内容缓存。测试在改动前就是红的则不下结论；有未提交修改的文件不碰。花的是 CPU，不是 token。

## Placement

层级不看目录名，看测试**需要什么才能跑**（Google 的 test size 思路）：驱动浏览器 → e2e；连 localhost、数据库、起子进程 → integration；渲染组件 → component；其余 → unit。目录声明的层级单独记录，两者不一致本身就是一条 finding。

规则的"性质"由词表判定它最低能在哪层被证明（纯逻辑 → unit，界面 → component，真实边界 → integration，整条流程 → e2e），模型可以修正；模型与词表不一致时该 finding 降为建议。

| 检查 | 含义 |
| --- | --- |
| `placement.too-high` | 纯逻辑规则只在 integration / e2e 被证明：每个边界值都要付一次浏览器或数据库的代价 |
| `placement.boundary-mocked` | 关于真实边界的规则只被 mock 掉边界的测试证明：测的是 mock |
| `placement.mislabelled` | 放在 unit 目录却需要网络 / 浏览器 / 子进程 |
| `placement.no-boundary` | 放在 integration / e2e 目录却什么边界都没跨：慢队列里的单元测试 |
| `placement.table-at-top` | 高层测试里跑大参数表：组合应当下沉 |
| `placement.pyramid` | 慢测试比快测试多 |
| `ci.level-not-run` | 某一层的测试没有任何 PR 步骤在跑 |

Placement 一节在报告里始终出现（各层文件数、用例数、PR 上跑了多少），即使 finding 都是 P2。

## 优先级与 gate

| 优先级 | 内容 |
| --- | --- |
| P0 | critical 规则没有测试（或只有被 skip 的测试）；critical 规则的限值在代码里被挪动后没有测试失败（执行证据）；测试不在 PR 上跑、或失败被忽略；仓库没有 CI |
| P1 | 其它规则没有测试；critical 规则的证明有洞（限值没测到、没有断言、不在 PR 上跑）；critical 规则 placement 不对；lint / type check 没强制；改动的高风险代码没有测试触达 |
| P2 | 非 critical 规则的洞和 placement；format、coverage、依赖扫描、密钥扫描 |
| P3 | 信息 |

审查对象始终是整个仓库。一条 finding 阻断，需要同时满足：优先级 ≥ `gate.fail_on`（默认 P1）；证据是 S 或 V；没有被 suppress（suppress 必须写理由，可带截止日期）。

带着存量问题起步的仓库可以打开棘轮（`gate.new_only: true`，Action 的 `new-only`）：默认分支每次运行写一份 baseline，之后只有 baseline 里没有的 finding 才阻断，其余照常报告。棘轮不改变审查范围，只改变哪些会让检查变红。

本地 hook 可以给一次改动（`--base` / `--staged`）：报告多出"改动的源码没有测试触达"和"触达改动代码的测试"两项，其它不变。

**试用期（GATE-27）。** 默认分支的每次运行会记下上一轮的 finding 去了哪：消失了算被修掉，被 suppress 算被忽略。某个检查项被忽略的比例超过 `gate.probation.max_dismissed`（且样本够 `min_resolved` 条），它就进入试用期：照常报告，不再阻断。这是 Google Tricorder 的做法——让使用者的反应决定一个检查配不配拦人，也是本工具在真实仓库上度量自己精度的地方。

同一个根因只报一条：测试检查本身没强制时，只有一条 `ci.tests`（P0），不再逐层、逐规则重复；某一层没有 PR 步骤在跑时，那一层的 finding 列出只在该层被证明的规则；同一份文档里四条以上规则有同一种缺口时，报告的表里合成一行。

finding 的指纹是"检查 + 对象"的哈希，不含行号和措辞，所以代码挪动不会让老问题变成新问题。

## 大仓库

- **不读源码。** 只读文档、测试、CI 文件和 manifest。文件清单来自 `git ls-files -s`，一次调用拿到全部路径和 blob 哈希。
- **增量。** 解析结果按 blob 哈希缓存（DEC-6），热缓存下 PR 只解析它改动的文件。
- **不做 规则 × 用例 的全量比较。** 候选检索走倒排索引：成本随"提到规则关键词的用例数"增长。
- **模型预算跨运行收敛。** 每次运行最多判定 `ai.max_rules` 条，最严重的先判，结果进缓存；下一次接着判剩下的。
- **上限都有，且会说出来。** 文档数、单文件大小、规则数、每次运行的模型调用数、报告每张表的行数都有上限；超出的部分在 Run 一节计数，完整列表在 findings.json。
- **monorepo。** 每个 manifest 目录是一个包；候选检索优先同包测试；`turbo run lint` / `nx run-many -t test` 会展开到各包的同名脚本。

## 精度：不引入噪音

宁可少报，不可错报。一条错的 P0 比十条漏掉的 P2 代价高，所以每一类 finding 都要回答"这凭什么成立"：

- **critical 要有把握。** token、role、retry、charge、delete 这类词只在某些语境里表示风险（"parser 的 token""按钮的 role 属性"）。单独一个这样的词不让规则成为 critical；两个，或任何一个不含糊的词（payment、password、webhook……）才算。
- **限值要是限值。** "from 1 to 2""after 3"这种介词加裸数字不算规则写明的限值；要有单位、货币符号或明确的比较词（at most、不超过）。
- **没人判断过的句子不进清单。** 无 ID 的规范性句子，在模型（或人）判定它是可测行为之前，只在 Proof 表里计数，不产生 finding。
- **团队没选的工具不算缺口。** 没有覆盖率、没有 SAST 只是 CI 表里的一行；"配置了没跑""失败被忽略""不在 PR 上跑"才是 finding，因为那是团队自己的决定没有被执行。
- **通过 helper 断言的测试不算"没有断言"。**
- **建议永远不是 P0，也永远不阻断。**

模型的注意力同理：只把代码定不了的那一小部分交给它，每一条只给决定结论的那几行，先问有真实候选的规则（模型的阅读在那里最有信息量），没有候选的排后面。

## 稳定性

- 同样的仓库状态 → 逐字节相同的报告（GATE-18）。迭代顺序全部排序，时间不进入结论。
- 模型结论走内容寻址缓存和锁文件：结论只在规则文本或候选测试变化时才可能变化。
- 候选的"弱相关"判定只看规则与测试共有的词数，不依赖语料统计：加一个无关的测试不会让别的规则在"没有测试"和"未核实"之间翻转。
- 阶段隔离（DEC-7）：坏掉的 YAML、超时的模型、不存在的 base commit，都只会让报告少一部分并写明原因。
- 退出码恒为 0，除非显式 `--enforce` 且 gate 判定 fail。
- 配置里的错字会被报告，对应项回落到默认值；不会因为配置错误静默关掉 gate。

### 评分卡（GATE-23）

`tests/fixtures/scenarios.js` 是 27 个变形场景：在 fixture 仓库里每次只埋一个缺陷（skip 掉证明测试、删掉断言、改了限值没改测试、给测试步骤加 `|| true`、去掉 `pull_request` 触发、把单元测试挪进 e2e 目录……）或做一次修复，并写明 finding 应该发生的**精确**变化。`tests/integration/eval.test.js` 逐个运行并打分：漏报算 recall，任何多出来的 finding 算 precision，两次运行不一致算不稳定。要求三项全满，且全程零模型调用。改词表、改阈值、改规则之前先看这张卡。

## 已知边界

- 默认测试只读不跑；执行证据要显式打开并给测试命令，且只覆盖写了数值限值的规则。
- 层级信号来自文件文本；把别的测试源码当字符串数据的文件（例如本仓库解析器的测试）会被误判，用 `suppress` 标注。
- 非 GitHub 的 CI（GitLab、Jenkins 等）只识别命令，不判断触发条件，报告中标为"runs, trigger not read"。
- 分支保护（哪些检查是 required）是仓库设置，本工具不读取。
- Rust 的 `#[cfg(test)]` 内联测试、Go 的表驱动子测试只做粗粒度识别。
