## 0. 结论先行：三个瓶颈各自的天花板

| 瓶颈 | 根因（调研结论） | 能做到的极致 | v0.2 的做法 |
| --- | --- | --- | --- |
| **LLM 稳定性** | 托管 API 在 temperature 0 下也不确定。根因是推理 kernel 没有 **batch invariance**：同一请求的数值结果取决于服务器当时把它和多少别的请求拼在一起（Thinking Machines 2025：Qwen3-235B T=0 跑 1000 次得到 80 种输出）。客户端改不了。另外，我们自己把 10–20 条规则拼进一个 prompt，同一条规则的判定会随邻居变化（2409.16022：批内条目相互污染；2309.00384：结果与位置显著相关） | **输入不变 → 判定逐字节不变（100%）**。不靠让模型确定，而是让同一个问题只问一次 | 逐条目的**内容寻址判定缓存**（verdict memo）：key = 模型 + prompt 版本 + 该条目看到的全部内容的哈希。没改的规则直接拿回上次的回复；只有输入变了的条目重新投票。投票时**每票打乱候选顺序**，只靠"排第一"赢的结论拿不到多数 |
| **精度** | 一个 80% 准的模型是好 reviewer、坏 gatekeeper。Google Tricorder：不被处理的提示超过 10% 就进观察期，超过 25% 下线；Meta Infer：同样的误报率，夜间批量报告修复率接近 0，改到 diff 时报告后超过 70% | **能阻断合并的结论，精度只受确定性证据的精度约束**，与模型准确率无关 | **证据分级 + 双钥匙规则**：E 执行 > S 代码 > V 模型提出、代码校验 > M 纯模型判断。默认只有 E/S/V 能阻断，M 只作建议。再叠加 Clean as You Code（只拦相对 baseline 新增的）+ 改动范围 + 有期限的 suppression |
| **Placement 不现实** | "纯计算应该下沉到单元测试"在逻辑上对，在工程上经常做不到：函数没导出、模块一 import 就读文件、连接在函数里 new 出来。Fowler 原话也是"能下沉就下沉，但更高层测试给的信心更大就留着"。调研**没有找到**任何关于"下沉可行率"的数据，这一块业界是空白 | **只在代码里找到 seam（可调用的接缝）时才给建议**；找不到就不提，而不是给一条没人能执行的建议 | `placement.js`：实现函数或它调用的同文件导出函数无 I/O → unit 直接调；只通过构造参数 / 全局 fetch 访问外部 → unit + fake；import 时就做 I/O、连接内建、未导出 → 不给 unit 建议。仓库里还没有该语言的单元测试 → 建议降级（要先搭测试环境） |

还有第四个天花板，它比上面三个都硬：**"测试是否断言了规则"本质上是语义问题，LLM 的上限有限（前身项目实测 missing test 精度 0–24%）。但它可以用执行来回答**：把实现函数体换成默认返回值（extreme mutation / pseudo-tested method，Niedermayr 1611.07163；28K+ 方法的复现见 1807.05030，所有被研究的项目里都有），再跑关联测试。还能过，就说明测试执行了代码但什么都没检查。这一步零模型方差。v0.2 把它作为可选的 E 级证据（`execute: true`）。

## 1. Unknown unknowns：大多数团队没意识到的 12 件事

按"对我们的影响 × 一般团队意识不到的程度"排序。每条：现象 → 证据 → 我们怎么处理。

1. **temperature 0 不等于确定。** 根因是服务端的 batch size，不是采样（Thinking Machines 2025；2408.04667：同一设置下准确率跨运行最多差 15%，最好与最差差 70%）。→ 不再追求"让模型稳定"，改为让不稳定**无关紧要**：verdict memo。
2. **我们自己的 batching 放大了不稳定。** 一个 prompt 判 12 条规则，改一条文档，另外 11 条的 prompt 也跟着变，判定一起重抽。邻居还会影响判定：前面的条目明显相关，后一条就被判得更严（2409.16022，所有被测模型都有）。→ memo 以**条目**为单位，不以 batch 为单位。只有输入变了的条目重新组 batch。
3. **位置偏差集中在势均力敌的候选上**（2406.07791）。光调换顺序，Vicuna-13B 就在 80 个问题里的 66 个上"赢过"ChatGPT（2305.17926）；对候选列表打乱再聚合有 +7–18% 的收益（2310.07712）。→ 第 k 票用种子 k 打乱代码候选、测试候选、测试块的顺序。prompt 里写明"顺序无意义"。
4. **3/3 全票不等于对。** 模型同时出错时，约 60% 选的是同一个错误答案，随机水平约 33%；越强的模型错得越相关（2506.07962）。没有外部校验器时，多数票不提升准确率（2603.06612）。→ 投票只用来压**方差**。**偏差**靠代码校验器（引用存在、import 可达、数字冲突）和执行。M 级永不单独阻断。
5. **"找不到测试"有两种，精度天差地别。** 全仓按规则 ID、术语、实现文件 import 检索都为空，这是确定性结论（S）；检索到了候选，模型逐个否掉，这是模型判断（M）。前身项目的 0–24% 精度几乎全是后一种。→ `strongCandidates` 计数区分两者。fixture 上 3 个 P0 "No test" 里只有 REQ-08 是 S，能阻断；REQ-11、DEC-06 降为建议。
6. **验证比寻找容易得多。** 让 LLM 验证一条给定的追溯链，准确率 98.87%；让它自己找，85.5%（TVR 2504.15427）。→ 我们的结构本来就是代码出候选、模型选择。下一步把"选择"进一步收窄成逐条二元验证（§5）。
7. **报告时机比精度更决定修复率。** Infer 同样的误报率，夜间批量修复率约 0，diff 时超过 70%。Google AutoCommenter 80% 的原始评论落在作者没改的行上，全部过滤掉。→ 改动范围过滤：finding 涉及的文件（规则文档、实现、关联测试、workflow）至少有一个在 PR 改动里，才能阻断。
8. **基线必须只减不增。** ESLint suppressions 和 Detekt baseline 都把"已知误报"和"已接受的债"分开。Sonar 只对 new code 设门槛。→ baseline 由默认分支的运行写入，PR 只对新增负责。suppression 必须有 reason 和 ≤1 年的到期日，过期自动复活。未知配置键直接报错（拼错一个键不能悄悄放松 gate）。
9. **指纹不能用规则 ID 和行号。** 文档上方插一条规则，REQ-7 就变成 REQ-8，所有 suppression 和 baseline 失效。GitHub code scanning 跨运行对齐告警，依赖稳定的 ruleId 和指纹。→ 指纹 = 哈希(section, 检查项, 归一化规则文本（去掉 ID）, part, 冲突对方文本)。重编号不变（有单测）。
10. **Mutation 的原始噪声高，要靠"arid"抑制。** Google 起步时 85% 的 mutant 没有产出，按开发者反馈抑制日志、超时、配置开关这类节点后，有产出的比例从 15% 升到 89%。不严格的启发式比严格的更有用。每行、每次评审都有上限，中位数是每个变更 2 个存活 mutant。整体 mutation score 与真实缺陷的相关性弱（Papadakis ICSE'18）。→ 我们**不算 mutation score**，只做**规则定向**的少量 mutant：极端 mutant + 限值 ±1 + 边界比较翻转。每条规则 ≤5 个，每次运行 ≤60 个。基线测试不绿就不下结论。
11. **LLM 看的是名字，不是语义。** 等价改写（重命名等）让性能最多掉 70%，10–50% 的正确答案推理是错的（2505.10443）。代码改写后，78% 原本能定位的缺陷定位不到了（2504.04372）。→ 名叫 `test_rejects_expired_token` 却什么都不断言的测试，模型容易判"断言了"。执行级证据不受这个影响。另有一票用混淆标识符的变体（§5 待做）。
12. **Test pyramid 本身有歧义，数据不支持"单元测试抓 bug 更多"。** 38,782 个测试里，单元和集成测试能抓到的缺陷类型没有差别，单元测试只是更好定位（Trautsch/Herbold/Grabowski，JSS 2020）。Google 按测试**用什么资源**定 size，而不是按名字。→ Placement 从"教条"改成"有 seam 才建议"。没有 seam 时，测试在集成或 e2e 层断言了规则并且在 PR 上跑，就算达标。

## 2. 架构：证明携带型 finding（proof-carrying findings）

```
                ┌─────────── 证据阶梯（能否阻断由证据定，不由严重度定）───────────┐
 finding ──► E  执行：规则定向 mutant 跑关联测试（存活 = 证明）                 可阻断
            S  代码：CI 解析、模糊词表、零候选检索、跳过标记、分支保护          可阻断
            V  模型提出 + 确定性见证：数字冲突、import 可达、seam、引用行存在   可阻断
            M  模型对语义的判断（带引用，过多数票）                            仅建议
                └───────────────────────────────────────────────────────────────┘
 gate = 严重度 ≥ fail_on  ∧  证据 ∈ {E,S,V}  ∧  不在 baseline  ∧  触及改动文件  ∧  未被有效 suppression
```

- **执行压过模型**：mutant 被杀，证明测试对规则敏感，覆盖模型的"没断言"；极端 mutant 存活，证明测试不检查，取代模型判断，basis = E。
- **报告完整，gate 克制**：报告照旧列出全部发现（mock 结构逐字不变），gate 只决定哪些能让 PR 变红。
- **不对称权限**（Semgrep、Uber 同款）：模型可以*加*建议、可以让候选*降级*，不能单独让一个 P0 阻断合并。

## 3. 与业界最好做法的对照：哪里是超越，哪里是追平

| 做法 | 谁做了 | 他们的边界 | 本项目 |
| --- | --- | --- | --- |
| 只报 diff、误报 <10% 才上线 | Google Tricorder / AutoCommenter | 针对代码规则，不涉及需求到测试的追溯 | 同样的"改动范围 + 新增"过滤，作用在**需求 → 代码 → 测试**链上 |
| 生成的测试必须能证明有改进 | Meta TestGen-LLM（build、5/5 通过、增加覆盖）、ACH | 用于**生成**，不用于**评审**现有测试 | 把同样的"可证明"标准用到**评审**：断言与否用 mutant 证明，不用模型意见 |
| 生成 → 独立打分 → 分类阈值 → 抑制低价值类别 | Uber uReview（75% 有用）、字节 BitsAI-CR（峰值精度 75%） | 精度上限约 75%，因为最终仍是模型判断 | 阻断集合里没有纯模型判断。模型判断的精度只影响建议区 |
| LLM + 静态路径约束消误报 | 腾讯（消除 94–98% 误报，召回 0.75–0.88） | 针对 SAST 告警 | 同样的"静态见证"思路用于追溯链（import 可达、数字冲突、seam） |
| 只对新代码设门槛 | Sonar Clean as You Code、Codecov patch | 指标是覆盖率、重复率，不涉及语义 | baseline 指纹对规则重编号稳定，suppression 带期限 |
| 让判定稳定 | 业界普遍做法是 temperature 0（无效，见 §1-1） | — | **内容寻址判定缓存**：同输入同判定。我们没有找到公开资料提到在 code review / quality gate 里这样做 |
| Placement 建议 | 普遍是测试金字塔教条 | 没有可行性数据 | **seam 分析**：只给能执行的建议 |

诚实的边界：上表的"超越"指**设计上**的。真实仓库上的精度要靠 §5 的遥测和人工标注来证明，目前只有 fixture 和文档召回基准的数字。

## 5. 已落地的调研结论与剩余工作

**已落地（v0.2.1）**

| 调研结论 | 落地 | 怎么用 |
| --- | --- | --- |
| 有用性遥测，每个检查项各自设观察期（Tricorder 不被处理率 ≥10% 进观察期；BitsAI-CR 用 Outdated Rate 作代理，规则要求约 25%，人工评论在 35–46%） | `scripts/usefulness.js` + `repo-report --history`。默认分支每次运行写一条历史（action 自动保存在缓存里，保留最近 100 条）。一个 finding 首次出现之后它的文件被改过、或者它消失了，就算被处理 | 处理率 < 0.25 且样本 ≥ 10 → 建议写进 `gate.probation`：照常报告，不再阻断。代理会漏算在别处修的情况，所以只给建议，不自动改配置 |
| 用 Learn-then-Test 定投票阈值（2110.01052），全票不等于正确（2506.07962） | `src/calibrate.js`（精确二项检验，从严到宽做固定序列检验）+ `scripts/calibrate.js`。每个 V/M finding 现在都记录投票一致率 `agreement` | 用金标 ledger 和多次运行跑出每个检查项的 `gate.min_agreement`。一致率低于阈值的 finding 不能阻断。样本不够时（目标 0.9、delta 0.1 至少要 22 条）明确说"不够，继续标注"，不乱给阈值 |
| 翻票条目单独复判（2505.12570；翻票说明条目处在边界上，§1-1） | `batchVotes` 的 `signature`：一个条目的几票判定不同，就把它单独拿出来、不带任何邻居再问一轮，以单独这一轮的结果为准。统计写在 `gate.json` 的 `splitVotes` | 四个模型阶段都已开启。只在 live 模式生效，回放时没有对应回复，不会触发 |
| Mutation 的 arid 列表（Google：有产出的 mutant 从 15% 升到 89%） | `execute.js` 的 `ARID`：日志、超时、指标、链路追踪、feature flag 所在的行不做 mutant。**规则本身讲的就是这件事时例外**（"网关调用 10 s 超时"照样会变异超时值） | 自动生效 |

**剩余工作**

1. **一票用混淆标识符**，专门抓靠名字通过的测试（§1-11）。要有一个对各语言都安全的重命名器，等 tree-sitter 接入再做。
2. **把"选择"改成"验证"**（TVR）：trace 阶段从"从候选里挑"改成"逐条回答这个测试是否测了这条规则"。调用会变多，靠 memo 摊薄。
3. **结论先还是理由先，做 A/B**（字节的验证器结论在前，精度 77%；前身项目实测理由在前更好）。现在有了 `calibrate.js`，可以按阶段用金标直接比较。
4. **tree-sitter**：seam 分析、函数体切分、import 现在都靠正则。
5. **跨文档的 superseded 关系**（"RFC 0011 取代 0005–0009"）。
6. **真实仓库的人工标注**：上面两个脚本都要靠真实标注才有意义，fixture 只能证明管线能跑通。

## 7. v0.3：投票成本，以及更往左的三步（2026-11-05）

### 7.1 投票的 token 成本

投票确实会加成本。v0.2 的实测：3 票让一次运行从约 2 AIU 涨到约 4 AIU，大约 2 倍；写报告文字的步骤只调一次，所以不到 3 倍。v0.3 加了四个手段把它压下来：

| 手段 | 做法 | 效果（fixture 的调用结构；真实花费要等 live 运行验证） |
| --- | --- | --- |
| 自适应投票 | 先问 2 票。两票一致就结束（一致率 2/2）；不一致就把条目单独拿出来，不带邻居问满 n 票（沿用 v0.2.1 的翻票复判） | 需要投票的调用从 24 降到 16（−1/3），整次运行从约 31 次降到约 23 次。每个翻票条目多 3 次 |
| Prompt caching | 每个阶段的 prompt 拆成两段：共享前缀（说明文字；judge 阶段还包括全部规则列表），加 `cache_control`；变化的条目放在后面。第一票先单独跑完写入缓存，其余票再并行，读缓存 | 缓存读按 0.1 倍计价。Haiku 5.5 的最小可缓存长度是 512 token，judge 阶段的规则列表通常超过它；trace、asserts 的前缀太短，不会被缓存（不报错，只是不生效） |
| 按阶段设票数 | `model.votes: { default: 3, built: 1 }`。纯模型判断（M）本来就不能阻断，可以少投 | 按配置 |
| Message Batches | `batch-api: 'true'`：只对默认分支的 baseline 运行生效，所有请求进 Message Batches，半价。PR 运行要低延迟，照常直接调用 | 那部分运行的花费减半，代价是要等几分钟到几小时 |

判定缓存（v0.2）仍然是最大的一项：只改代码不改文档的 PR，第 1–2 节的判定全部命中缓存。

### 7.2 diff 级的规则影响分析（`src/impact.js`，全部确定性）

PR 的 diff 加上 ledger 里的规则 → 代码 → 测试映射，由代码直接判三件事：

| 检查 | 条件 | 证据 |
| --- | --- | --- |
| Unguarded change | 改动落在某条规则的实现函数体里，而这条规则没有达标的测试守护（达标 = 有关联测试、断言了规则、在 PR 上运行） | V（实现位置由模型定，代码校验过）；关联测试全是标记时为 S |
| Code drifts from spec | 实现文件或规则点名的文件里，某个改动行把规则写明的限值换成了别的数（30 → 45），而规则文档不在这次改动里 | 规则点名的文件为 S，否则 V |
| Spec drifts from code | 改动把规则所在行的数字改了（45 → 60），实现函数体和它用到的常量里还是旧值、没有新值 | 同上 |

另外输出 `affected.json` 和 action 的 `affected-tests`：这次改动碰到了哪些规则、守护它们的测试是哪些，可以先跑这些。

开启执行证据时，mutant 只做在实现被改动的规则上，PR 上几十秒就能跑完，和 Google 只在评审时对改动行做 mutant 的思路一样。

fixture 上的例子：一个 PR 把 `validateExcess` 里的 `>=` 改成 `>`，同时把 `RETENTION_DAYS` 从 30 改成 45。结果是两条 P1：REQ-02 Unguarded change（关联的单元测试不达标），REQ-04 Code drifts from spec（文档仍写 30 天）。

### 7.3 让追溯链变成显式标记（`src/construct.js`）

- **标记**：模型全票给出、并且代码校验过（import 可达）的链接，生成一个补丁，在测试用例上方插入一行 `// covers REQ-07`。合进去以后，这条链由代码按标记找到，以后不再需要模型。模型的工作量随每次采纳单调减少。三条限制：只对源文档里本来就写了 ID 的规则（按顺序编号的 ID 会随插入而移动）；"Calls the code" 失败的测试不生成标记（不把错的链接固定下来）；只用全票的链接。
- **待实现测试**：没有测试的规则（有 diff 时只限这次改动新增的规则行），在仓库最常用的单元测试目录和语言下生成待实现测试：`it.todo`、pytest skip 或 Go `t.Skip`，测试名带规则 ID，并逐条写出边界值。合进去以后，"No test" 变成"Not skipped"，等实现规则的 PR 把它变绿。这就是由 gate 强制的测试先行。
- **边界值表**：从规则的限值和文字里的上限、下限、区间用词，直接用代码生成"正好在边界上、刚越过边界"的用例。"from $500 to $5,000" 生成 499.99 拒绝、500 接受、5000 接受、5000.01 拒绝；文字没说哪边允许时，期望结果留空，不替文档拿主意。PR 评论里附上对应语言的 `it.each` 或 pytest `parametrize` 片段。

输出：`construct.patch`（可以直接 `git apply`）和 `construct.json`。

### 7.4 前移到写代码的时候（`agent/`）

- `agent/mcp-server.js`：手写的 MCP stdio 服务（JSON-RPC 2.0，协议版本 2025-06-18），提供三个工具：`rules_for_file`、`rule`、`impact`。
- `agent/after-edit-hook.js`：Claude Code 的 PostToolUse hook。agent 每编辑一个文件，就把这个文件承载的规则、限值、守护测试、未解决的问题作为 `additionalContext` 告诉它；没有测试的规则会写 "NO TEST: add one that names the rule ID"。hook 永远不会阻断编辑。
- 两者都读 gate 产出的 `ledger.json`。配置方法见 `agent/README.md`。

### 7.5 还没验证的

- 自适应投票和 prompt caching 的实际省钱幅度：要看 live 运行的 `usage.cache_read_input_tokens` 和 `gate.json` 里的 `votes`。
- Batch API 的端到端运行：只用桩测试过请求分组、按 `custom_id` 对应结果、半价计费。
- 在真实仓库上，标记的采纳率，以及待实现测试会不会被团队接受：这是这个方向成败的关键，要看团队愿不愿意在测试里加规则 ID。
