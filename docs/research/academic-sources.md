## 1. Nondeterminism at temperature 0

| Source | Finding | Numbers | Implication |
|---|---|---|---|
| Thinking Machines Lab, Horace He et al., "Defeating Nondeterminism in LLM Inference", 2025-09-10. https://thinkingmachines.ai/blog/defeating-nondeterminism-in-llm-inference/ | The root cause is not "concurrency + floating point" in general. Kernels are not **batch-invariant**: a request's numerics depend on the batch size it is served in, and that depends on server load. The forward pass itself is run-to-run deterministic. | Qwen3-235B, T=0, 1000 runs gave 80 unique completions. The first divergence was at token 103 (992 vs 8). Batch-invariant kernels gave 1000/1000 identical, at about 1.6x slower (26s → 42s) in unoptimized vLLM. | Hosted APIs will stay nondeterministic at T=0 and there is nothing we can do about it client-side. Treat each call as a sample, not as a function. Instability is concentrated on **near-tie items**, because a tiny logit change flips the argmax. So flip-flopping across votes is itself a useful "borderline item" signal. |
| Atil et al., "Non-Determinism of 'Deterministic' LLM Settings", arXiv:2408.04667 | 5 LLMs, 8 tasks, 10 runs, all with "deterministic" settings. No model was repeatable across all tasks. | Accuracy varied by up to 15% across runs. The best-to-worst gap was up to 70%. They define TARr@N (raw string agreement) and TARa@N (parsed-answer agreement). | Measure **TARa@N on parsed verdicts** per item class as a CI health metric. Raw-string agreement is the wrong target. |

| arXiv:2502.20747, "Measuring Determinism in Large Language Models for Software Code Review" | GPT-4o-mini, GPT-4o, Claude 3.5 Sonnet and LLaMA 3.2 90B were run 5 times each at T=0 with cleared context on 70 Java commits. All of them varied. | Exact rates are not in the abstract. [UNVERIFIED author attribution: I did not record the author list.] | This is direct evidence for our domain (code-review judgments). |

[UNVERIFIED from memory: the body notes that capacity-limited sparse MoE is not per-sequence deterministic, because tokens from different sequences in a batch compete for expert slots.] | none | This is a second mechanism by which batch co-tenants change your output on MoE-served models. ## 2. Prompt composition: batching, position, order

| Source | Finding | Numbers | Implication |
|---|---|---|---|
| Cheng, Kasai, Yu, "Batch Prompting", arXiv:2301.08721 | Batching k samples per prompt cuts cost almost inverse-linearly and keeps accuracy. | Up to 5x token and time savings with 6 samples per batch. Performance depends on batch size and task complexity. | This is the baseline justification for batching. It measures **accuracy, not per-item stability or cross-item influence**. |
| Lin et al., "BatchPrompt: Accomplish more with less", arXiv:2309.00384 | Batched prompting is **worse** than single prompting in long contexts, and performance is "significantly correlated with the positions and order of the batched data". The fix is **Batch Permutation and Ensembling (BPE)**: re-run the batch with permuted order and vote. SEAS adds early stopping. | At batch size 32, BPE matched or beat single prompting using 9–16% of the calls (BoolQ 90.6→90.9%). | **This directly fits our design.** Our 3 votes should use **3 different item orders (and ideally different batch compositions)**, not 3 identical prompts. Then the votes decorrelate position effects instead of repeating them. |
| Korikov et al., "Batched Self-Consistency Improves LLM Relevance Assessment and Ranking", arXiv:2505.12570 | Batched pointwise judging combined with self-consistency over **varied batch permutations and compositions** beats one-by-one judging. | GPT-4o legal search NDCG@10: 43.8→51.3% (1 vs 15 SC calls), vs 44.9→46.8% one-by-one, which was also 15.3x slower. | Same remedy as BatchPrompt. It is evidence that batching is fine *if* you shuffle across votes. |
| Chen et al., "AI Can Be Cognitively Biased: Threshold Priming in LLM-Based Batch Relevance Assessment", arXiv:2409.16022 | **Cross-item contamination exists.** LLMs give lower scores to later items when earlier ones were highly relevant, and the reverse. This held for every model (GPT-3.5, GPT-4, Llama2-13B/70B) and every batch length. | Direction holds across all combinations (abstract). | In a batch of 10–12 rules, a run of clear "PASS" items can push a borderline item toward "FAIL", and vice versa. Remedies: shuffle per vote, mix easy and hard items, and consider a **neutral fixed anchor item** or re-judging flip items alone. |
| "Efficient but Vulnerable: Batch Prompting Attack", arXiv:2503.15551 | Instructions injected into one batch item interfere with **all** items in the batch. All LLMs tested were susceptible. Prompt-based defense was weak; probing detected about 95%. | 150 attacks, 8k batch instances. | Security issue for a quality gate: an adversarial string in a PR test file or comment can flip verdicts for other rules in the same batch. Isolate untrusted file content with delimiters, keep batches per-file or per-PR-author-trust, and verify citations in code (already done). |
| Wang et al., "Large Language Models are not Fair Evaluators", arXiv:2305.17926 | Changing the order of candidates in the prompt changes the verdict. | Vicuna-13B beat ChatGPT on 66/80 queries just from order. Fixes: evidence-before-score, **Balanced Position Calibration** (average over swapped orders), and human-in-the-loop when position-entropy is high. | "Evidence first, verdict last" in the schema (cite path:line, then decide). Treat order-dependent disagreement as abstain. |
| Shi et al., "Judging the Judges: Position Bias in LLM-as-a-Judge", arXiv:2406.07791 | 15 judges, >150k instances. Position bias is not random. It varies by judge and task and is **strongly driven by the quality gap between candidates**, while prompt length matters only weakly. Metrics: repetition stability, position consistency, preference fairness. | none in abstract | Position bias concentrates on **close calls**, which are exactly the items that fail our precision target. Report "position consistency" per item. |
| Liu et al., "Lost in the Middle", arXiv:2307.03172 | Accuracy is U-shaped over position. Relevant info in the middle of long contexts is used worst, even by long-context models. | none in abstract | For "which candidate file implements this rule", the candidate list order matters. Put the strongest deterministic candidate (e.g. by grep or symbol match) first and rotate the rest across votes. |
| Tang et al., "Found in the Middle: Permutation Self-Consistency", arXiv:2310.07712 | Shuffle the list order across calls and aggregate to the central (Kemeny-style) ranking. They prove convergence under random perturbation. | +7–18% (GPT-3.5), +8–16% (Llama2-70B). | Use this for candidate-file selection: vote across permutations, not repeats. |

## 3. Calibration, abstention, agreement

| Source | Finding | Numbers | Implication |
|---|---|---|---|
| Xiong et al., "Can LLMs Express Their Uncertainty?", arXiv:2306.13063 | Verbalized confidence is overconfident. Consistency across samples is better. All methods struggle on specialized-knowledge tasks. | Black-box vs white-box AUROC 0.522 vs 0.605. | Don't put a `confidence` field in the schema and trust it. Use vote agreement plus deterministic checks. |
| Kim, Garg, Peng, Garg, "Correlated Errors in Large Language Models", arXiv:2506.07962 (ICML 2025) | Models agree on the **same wrong answer** about 60% of the time when both err (chance would be about 33%). More accurate models are **more** correlated, even across providers. | 350+ LLMs. | **A unanimous 3/3 vote is not independent evidence**, and swapping in other vendors' models helps less than expected. Agreement only bounds variance, not bias. Measure precision of 3/3 verdicts on labeled data; don't assume it. |
| "Consensus is Not Verification", arXiv:2603.06612 (2026) | Polling-style aggregation gives no consistent accuracy gain over a single sample even at 25x compute, and often amplifies shared misconceptions. It does work in domains *with* external verifiers. | 5 benchmarks. | Our advantage is that we **have** verifiers (citations checked against code, tests runnable). Push decisions onto verifiable claims, and use majority voting only as a stability filter. |
| Yadkori et al., "Mitigating LLM Hallucinations via Conformal Abstention", arXiv:2405.01563 | Use self-consistency similarity as the score and conformal calibration of the abstain threshold to get a **guaranteed bound on error rate**. | Bounds hallucination rate on QA sets. Less conservative than log-prob baselines. | Recipe: on a labeled calibration set of about 200–500 items, pick the vote-agreement threshold so that P(error and not abstain) ≤ α. Output "unknown" below it. |
| Quach et al., "Conformal Language Modeling", arXiv:2306.10193 | Conformal stopping and rejection rules for sampling produce sets that contain an acceptable answer with high probability, plus component-level guarantees. | none | Use when you want "set of candidate files guaranteed to contain the implementer" rather than one answer. |
| Angelopoulos, Bates, Candès, Jordan, Lei, "Learn then Test", arXiv:2110.01052 | Calibrate any thresholded predictor to satisfy finite-sample risk control (e.g. **FDR / precision**), recast as multiple hypothesis testing. | none | This is the right framework for "precision ≥ 95% on emitted FAIL findings". Tune (vote-threshold, perturbation-agreement, deterministic-check) jointly with LTT on a held-out labeled set. Caveat: it assumes exchangeability, so recalibrate per repo or language family. |
| "When LLMs agree, are they right?" | **Not found** as a titled paper. The closest are 2506.07962 and 2603.06612 above. | | |

## 4. Metamorphic / perturbation stability of code judgments

| Source | Finding | Numbers | Implication |
|---|---|---|---|
| Orvalho & Kwiatkowska, "Are LLMs Robust in Understanding Code Against Semantics-Preserving Mutations?", arXiv:2505.10443 | Variable renaming, mirrored comparisons, swapped if/else, for→while and loop unrolling all change predictions. 10–50% of correct predictions rested on flawed reasoning. | Performance drops up to 70% (v3 abstract). | Being right in one run doesn't mean the reasoning is sound. A **metamorphic vote** (judge the original plus one renamed or reformatted variant) catches lucky-correct verdicts. |
| "Assessing the Impact of Code Changes on the Fault Localizability of LLMs", arXiv:2504.04372 | Semantics-preserving mutations made LLMs **fail on 78%** of faults they had previously localized. Reasoning is better when relevant code appears **earlier** in context. | 10 LLMs, 750,013 tasks, Java and Python. | This is the closest analogue to "find the line that implements rule X". Expect large instability. Put the cited region first, and use perturbation agreement as a precision filter. |
| "When Names Disappear", arXiv:2510.03178 | Removing identifier names degrades even execution tasks. Models lean on naming. | ClassEval-Obf benchmark. | For "does this test assert the rule", a test named `test_rejects_expired_token` can earn a PASS without asserting anything. Renaming tests and helpers to opaque names in one vote is a cheap check for **name-driven false positives**, which likely cause a large share of our precision loss. |

|---|---|---|---|
| Niedermayr, Juergens, Wagner, "Will My Tests Tell Me If I Break This Code?", arXiv:1611.07163 (CSED 2016) | **Pseudo-tested methods** are covered, but removing the whole method body fails no test. | Source | Finding | Implication |
|---|---|---|

**No paper found that reports precision at high-confidence thresholds for requirement→test linking.** This is a gap. We would need to produce that curve ourselves (precision vs vote agreement), e.g. with Learn-then-Test.

## Synthesis: remedies most teams miss
1. **Votes must be decorrelated, not repeated.** Permute item order *and* batch composition across the 3 votes (BatchPrompt BPE, 2505.12570, 2310.07712). Identical prompts only sample server batch noise, and they re-sample the same position and priming bias.
2. **Batch neighbours are a hidden variable.** Threshold priming (2409.16022) and injection spillover (2503.15551) mean a verdict depends on its batch-mates. Re-judge flipping items alone.
3. **3/3 agreement ≠ correct.** Errors are correlated (2506.07962, 2603.06612). Calibrate thresholds on labeled data with conformal / LTT (2405.01563, 2110.01052), and emit `unknown` below threshold.
4. **Metamorphic vote.** One vote on a renamed or obfuscated variant catches name-driven false PASSes (2510.03178, 2505.10443, 2504.04372).
5. **Replace judgment with execution where possible.** Extreme mutation / pseudo-tested detection (1611.07163, 1807.05030, Descartes) answers "does the test assert this behaviour" deterministically. Keep the LLM for locating the method and for equivalent-mutant triage (2408.01760).
6. **Deterministic pre-filters**: tsDetect-style no-assertion / empty-test checks, resource-based test sizes, and "mocks the subject under test".
7. **Track TARa@N per check type** in CI (2408.04667) as an instability SLO. Expect instability to sit on near-tie items (Thinking Machines; 2406.07791 quality-gap finding).
